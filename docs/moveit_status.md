# MoveIt configuration state

The original MoveIt packages for this robot were never in this repo, so
`aico2_moveit_config` was written here from scratch. It now runs on hardware:
`move_group`, RViz interactive-marker planning, command-line goals via
`moveit_goal.py`, and trajectory execution on both arms and the waist.

For how to use it, see [`../README.md`](../README.md) §5.8. This file covers
what the configuration is derived from and where it is incomplete.

## Files

| File | Contents |
| ---- | -------- |
| `config/aico2.srdf` | generated by `scripts/generate_srdf.py` |
| `config/kinematics.yaml` | KDL IK for `left_arm`, `right_arm`, `left_arm_waist` |
| `config/joint_limits.yaml` | every group joint, within the URDF limits |
| `config/moveit_controllers.yaml` | maps each group to a driver's `follow_joint_trajectory` |
| `config/ompl_planning.yaml` | RRTConnect per group |
| `config/moveit.rviz` | includes the `Interact` tool, needed for the goal-state marker |

## Planning groups

| Group | Chain | IK |
| ----- | ----- | -- |
| `left_arm` | `Left_link0` → `Left_flange` | yes |
| `right_arm` | `Right_link0` → `Right_flange` | yes |
| `left_arm_waist` | `base_link` → `Left_flange`, so both waist axes plus the left arm | yes |
| `both_arms` | `left_arm` + `right_arm` | **no** |

`both_arms` has an OMPL config but no `kinematics.yaml` entry. Selecting it in
RViz gives no interactive marker, and planning its 14 DoF took ~123 s. Use the
single-arm groups.

## The waist

`AGV_Joint1/2` were declared `<passive_joint>` while nothing in ROS could
command them. They are now commandable: the left arm driver owns them under
`control_waist:=true` and accepts them in a `follow_joint_trajectory` goal, so
they belong to `left_arm_waist` and a passive declaration would make MoveIt
refuse to plan them.

With `control_waist:=false` the driver silently drops the waist columns from a
9-joint goal and moves only the arm. The goal still reports success.

## The collision matrix is partial, by construction

`generate_srdf.py` disables only what it can derive from the URDF — 83 pairs:

| Reason | Count | Basis |
| ------ | ----- | ----- |
| `Adjacent` | 33 | share a joint |
| `Welded` | 50 | rigidly connected through fixed joints |

It does **not** disable the two categories that need geometric reasoning:
pairs that can never collide anywhere in the reachable workspace, and
`Default` pairs already colliding at the zero state. A real MoveIt setup
assistant finds those by sampling.

Consequence: planning is more conservative than the hardware requires, and a
start state can be rejected over a pair that is physically fine. When
`CheckStartStateCollision` aborts a plan, `move_group` names the contacts in
its log but the action only returns a generic `FAILURE`. To get the contacts
as data:

```bash
python3 src/aico2_moveit_config/scripts/check_collisions.py
python3 src/aico2_moveit_config/scripts/check_collisions.py --named ready
python3 src/aico2_moveit_config/scripts/check_collisions.py --joint 4 --degrees -15
python3 src/aico2_moveit_config/scripts/check_collisions.py --emit-srdf
```

`--emit-srdf` prints ready-to-paste `disable_collisions` lines. Add them to
`generate_srdf.py`, not to the generated SRDF, or the next regeneration drops
them.

If the original packages ever turn up, their SRDF is still worth taking — the
full collision matrix is the one part that cannot be derived from the URDF.

## Validation without hardware

```bash
python3 src/aico2_moveit_config/scripts/check_config.py
colcon test --packages-select aico2_moveit_config
```

`check_config.py` cross-checks the SRDF, kinematics, joint limits and
controller entries against the URDF: every group joint present and within its
URDF limit, an IK solver per group that needs one, and controller joint lists
matching the drivers. It accepts the driver joints optionally followed by the
waist joints, since the left controller gains them under `control_waist`.

## Known gaps

- Visual meshes: four `.obj` files and six `.mtl` files are absent from the
  repo, so the URDF points those visuals at the collision STLs. Geometry is
  correct; appearance is not.
- `longest_valid_segment_fraction: 0.005` is unusually tight. 0.01–0.02 would
  plan 2–4× faster, but collision-checking resolution is a deliberate
  trade-off and was left alone.
- Execution smoothness **was** a MoveIt-side problem, not driver-side as
  previously recorded here. `AddTimeOptimalParameterization` saturates
  acceleration, so jerk is unbounded at the velocity profile's corners;
  `AddRuckigTrajectorySmoothing` and the jerk limits in `joint_limits.yaml`
  fix it. See [`open_issues.md`](open_issues.md) issue 1.
- The post-move settle delay is driver-side and still open —
  [`open_issues.md`](open_issues.md) issue 2.
