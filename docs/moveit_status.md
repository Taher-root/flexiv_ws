# MoveIt status in this workspace

Short version: **the original MoveIt packages are not in this repo, so
`aico2_moveit_config` was written from scratch.** It is complete and
statically cross-checked, but it has never been run. The collision matrix is
partial by construction — see below.

## What is absent

No SRDF. No `kinematics.yaml`. No `joint_limits.yaml` for MoveIt. No
`move_group` launch file. No `moveit_controllers.yaml`. No moveit_config
package at all. Nothing in git history either — these were never committed
here.

The four servo YAMLs name their missing counterparts in their own header
comments:

```
# Pair with: aico2_bringup/mock_moveit_servo.launch.py
#            aico2_vr_teleop/teleop_moveit_servo.launch.py
```

Neither `aico2_bringup` nor `aico2_vr_teleop` is in `src/`. And
`left_arm.yaml` refers to "the SRDF 'ready' state (joint6=+pi/2)", so an SRDF
exists somewhere — on the VR teleop machine, most likely, alongside those two
packages.

**So the first question is not "why doesn't the MoveIt code work" but "where
is it".** It is probably on one of the other two machines (the VR teleop host,
or one of the non-git `flexiv_ws` checkouts). Finding it beats rewriting it:
it already encodes the collision pairs and named states this robot needs.

## The URDF is ready for it

Checked, and it does not need changes to support a moveit_config:

- Single root link `base_link`, one connected tree, 30 links.
- 16 revolute joints: `AGV_Joint1/2` (waist), `Left_joint1..7`, `Right_joint1..7`.
- Both arms hang off `AGV_Pitch` via fixed `Left_Joint0` / `Right_Joint0`, so
  the waist is in each arm's kinematic chain but not in an arm planning group —
  it moves the arm base, which MoveIt handles as long as `/joint_states`
  carries the waist (it does, since `aico2_waist_driver`).
- Tips are `Left_flange` / `Right_flange` via fixed `*_link7_to_flange`.
- Every revolute joint has `<limit lower= upper= effort= velocity=>`, e.g.
  `Left_joint1` ±2.8798 rad, effort 123, velocity 2.0944.

## Checking the half that does exist

`src/aico2_left_arm_driver/scripts/check_arm_ros.py` verifies the ROS arm
stack in the order things fail: node present in the expected namespace,
lifecycle `active`, `/joint_states` flowing with this arm's seven joints and
how many publishers are contributing, and the `follow_joint_trajectory` server
up. With `--send-goal --yes-move` it builds a two-point trajectory from the
live joint positions and sends it, then reports the error code and how far the
joint actually moved.

```
source /opt/ros/jazzy/setup.bash
python3 check_arm_ros.py                                   # checks only
python3 check_arm_ros.py --send-goal --yes-move             # moves joint 4 by 15°
python3 check_arm_ros.py --namespace right_arm
```

A pass is the prerequisite for MoveIt, not a substitute: `move_group`
ultimately just sends goals to that same action server. If this fails, MoveIt
would fail for the same reason and tell you less about why.

## What was built, and what it still needs

`src/aico2_moveit_config/` now contains:

| File | Notes |
| ---- | ----- |
| `config/aico2.srdf` | generated by `scripts/generate_srdf.py`; groups `left_arm`, `right_arm`, `both_arms`; `home` / `ready` states; waist declared `passive`; 66 collision pairs disabled |
| `config/kinematics.yaml` | KDL (ships with MoveIt); commented `pick_ik` block to swap in |
| `config/joint_limits.yaml` | velocities from the URDF, accelerations added (the URDF has none) |
| `config/moveit_controllers.yaml` | `MoveItSimpleControllerManager`, `moveit_manage_controllers: false` |
| `config/ompl_planning.yaml` | RRTConnect per group |
| `launch/move_group.launch.py` | loads the URDF from `flexiv_amr_description` by absolute path |
| `launch/moveit_rviz.launch.py` | + `config/moveit.rviz` |
| `scripts/check_config.py` | cross-checks all of the above against the URDF and the drivers |

`scripts/check_config.py` passes all 15 checks. It verifies the things that
otherwise surface as "planning works, execution finds no controller": SRDF
links and joints existing in the URDF and being actuated types, controller
joint lists matching the drivers' `joint_names` **in order**, controller names
resolving to `/left_arm/follow_joint_trajectory` (MoveIt builds the action as
`<controller_name>/<action_ns>`, so naming them `*_controller` would break
execution silently), `joint_limits` covering every group joint without
exceeding the URDF, and kinematics/OMPL entries per group.

What it cannot verify, and what therefore remains unproven: that MoveIt loads
these files without complaint, that KDL finds IK for real targets on a 7-DoF
arm, and that a planned trajectory executes through the driver. Those need the
robot.

### The collision matrix is the known gap

66 pairs are disabled, all derived from the kinematic tree: `Adjacent`
(parent/child across a joint) and `Welded` (rigidly connected through fixed
joints). The MoveIt Setup Assistant's other two categories — `Never` (never
collides anywhere reachable) and `Default` (already colliding at zero) — need
geometric sampling against the meshes.

Consequences: planning works, but every state check tests pairs that can never
collide, so it is slower than it needs to be, and self-collision checks between
the two arms and the AMR body are conservative — MoveIt may refuse poses that
are physically fine. One pass with the Setup Assistant on this URDF, merging
its `disable_collisions` block into `config/aico2.srdf`, fixes both.

### Two robot-specific traps

- The waist (`AGV_Joint1/2`) is commanded by nothing in ROS; `aico2_waist_driver`
  only reads it. It is declared `passive` so MoveIt treats it as a moving base
  via `/joint_states`. Putting it in a planning group requires a command path
  first.
- The driver rejects any trajectory omitting one of the seven joint names
  (`reorder_to_driver`), and rejects everything while teleop is active. A group
  planning for a subset of an arm's joints is rejected outright, not partially
  executed.

## Compliant execution through MoveIt

The driver now takes `joint_control_mode: impedance`, which switches the
trajectory and servo paths to `NRT_JOINT_IMPEDANCE` and applies
`joint_stiffness_ratio * K_q_nom` on the arm axes after the mode switch (the
order matters: `SetJointImpedance` is only applicable once in that mode). The
ratio is a live parameter:

```bash
ros2 param set /left_arm/left_arm_driver joint_stiffness_ratio 0.3
```

MoveIt is unaware and unaffected — the trajectories and the action are
identical, only the controller tracking them inside the robot changes. See
`docs/rdk_version_and_compliance.md`.
